# Deploying to the dev site

The dev site is <https://dev.cularcreative.com/foundationmarketing> — a WordPress
install in a **subdirectory**, behind Cloudflare.

Deployment is `.github/workflows/deploy-dev.yml`: GitHub Actions builds the four Vite
targets and rsyncs the result over SSH. It runs on every push to `main`, and can be run
by hand from the Actions tab against any branch.

> **Why a build step and not just a file copy.** `theme/build/` and `plugin/build/` are
> gitignored, and Node never runs on the server. The repo on its own is not a deployable
> site — without a build there is no CSS and no JS at all.

---

## 1. What it deploys, and what it does not

| | |
|---|---|
| `theme/` → | `<wp>/wp-content/themes/foundations/` |
| `plugin/` → | `<wp>/wp-content/plugins/foundations-blocks/` |

**Excluded:** `theme/src/` (build-time only), `plugin/src/styles/`, `*.scss`, `*.jsx`,
`node_modules/`, `.git*`.

**`plugin/src/blocks/` is deliberately NOT excluded.** `plugin/inc/register.php`
discovers blocks at runtime by scanning `plugin/src/blocks/*/block.json`, and each
`block.json` points at its own `render.php`. Excluding `plugin/src` would unregister
every block on the server and every section would render as nothing.

**It does not touch:** the database, `wp-content/uploads`, any other theme or plugin,
`wp-config.php`, or `.htaccess`. Content, menus, and the palette setting are *not*
deployed — those live in the database and are set in WP Admin.

**It does not activate anything.** After the first deploy, go to WP Admin →
Appearance → Themes and activate *Foundations*, and Plugins → activate
*Foundations Blocks*. The dev site is currently running `hello-elementor` +
`hello-theme-child-master` with Elementor, so nothing changes until you switch it.

## 2. One-time setup

### 2.1 Turn on SSH at Bluehost

cPanel → **SSH Access** → *Manage SSH Keys*. Note the **port** — Bluehost shared hosting
often uses **2222**, not 22.

### 2.2 Make a deploy keypair

Generate it locally. Use a key made **for this one purpose** — never your personal key.

```bash
ssh-keygen -t ed25519 -C "github-actions deploy to dev" -f ./fm-deploy -N ""
```

That writes `fm-deploy` (private) and `fm-deploy.pub` (public).

- Paste the contents of **`fm-deploy.pub`** into Bluehost → SSH Access → Import Key,
  then **Authorize** it.
- The contents of **`fm-deploy`** become the `DEV_SSH_KEY` secret below.
- Delete both local files once the secrets are saved. `fm-deploy*` is gitignored, but
  do not rely on that.

### 2.3 Pin the host key

This stops the deploy from trusting whatever answers on that address:

```bash
ssh-keyscan -p 2222 dev.cularcreative.com     # use your real port
```

The output is the `DEV_SSH_KNOWN_HOSTS` secret.

### 2.4 Find the absolute path to the install

SSH in and ask WordPress where it lives:

```bash
ssh -p 2222 USER@dev.cularcreative.com
cd ~/public_html/foundationmarketing && pwd    # adjust until wp-config.php is there
ls wp-config.php wp-content/themes             # both must exist
```

The `pwd` output is `DEV_WP_PATH`. The workflow refuses to run if `wp-config.php` is not
found there — that check is what makes `rsync --delete` safe to use.

### 2.5 Add the secrets

**This repository is public**, so every one of these must be a secret, never a value in
the workflow file. Settings → Secrets and variables → Actions → *New repository secret*:

| Secret | Example | From |
|---|---|---|
| `DEV_SSH_HOST` | `dev.cularcreative.com` | your host |
| `DEV_SSH_PORT` | `2222` | cPanel → SSH Access |
| `DEV_SSH_USER` | `cularcre` | cPanel username |
| `DEV_SSH_KEY` | `-----BEGIN OPENSSH PRIVATE KEY-----…` | §2.2, the whole file |
| `DEV_SSH_KNOWN_HOSTS` | `dev.cularcreative.com ssh-ed25519 AAAA…` | §2.3 |
| `DEV_WP_PATH` | `/home/cularcre/public_html/foundationmarketing` | §2.4 |

Secrets are not exposed to workflows triggered by pull requests from forks, and this
workflow only runs on `push` to `main` and on manual dispatch, so a fork cannot reach
them.

## 3. Running it

**Automatically:** merge to `main`.

**By hand:** Actions → *Deploy to dev* → *Run workflow* → pick the branch. This is how
to deploy a feature branch without merging it.

**Dry run first.** The manual form has a *Dry run* checkbox. It runs the real build and
the real preflight, then asks rsync to list what it would change and write nothing.
Use it for the first run, and any time `DEV_WP_PATH` changes.

## 4. Known gotchas on this particular site

**The error-page `.htaccess` snippet is written for a domain root.**
`theme/errors/htaccess-snippet.txt` emits paths like
`/wp-content/themes/foundations/errors/403.html`. The dev install is in a subdirectory,
so those need `/foundationmarketing` in front of them or the error documents 404. The
snippet is generated by `scripts/build-error-pages.mjs` and is a manual paste either
way — see the file's own header.

**`wp-login.php` currently returns 409 Conflict** through Cloudflare. That is not caused
by the deploy, but it will stop you reaching WP Admin to activate the theme. Check the
Cloudflare WAF rules or the site's security plugin first.

**Production is a separate problem.** `doc/SECURITY-PRODUCTION-CLEANUP.md` records that
the live Bluehost site is very likely still infected. This workflow deploys to dev only,
deliberately. Do not copy it to a production target until that cleanup is done.
